## Findings log

### F1 — Preflight should ask one question at a time
- **Phase:** 0 (Preflight) — `or-preflight-1`.
- **Observation:** Preflight, following `assets/preflight-brief.md` Step 2 ("*In one short plain-text message … ask the user for **both**…*"), bundles the worktree-name question and the base-branch question into a single turn. The tester found this suboptimal: **preflight should ask one question at a time** — ask the worktree name, wait for the answer, then ask the base branch, wait — rather than presenting multiple questions in one message. (Mode-disambiguation, when it fires, is a third sequential question.)
- **Why it matters:** Setup dialogue clarity. One-question-at-a-time is easier for the user to answer cleanly and avoids partial/ambiguous replies; it also matches a more natural conversational cadence for a teammate that owns its own pane.
- **Source of the behavior:** `assets/preflight-brief.md` Step 2 explicitly instructs asking for *both* in one message.
- **Candidate fix (not yet actioned):** Revise `preflight-brief.md` Step 2 to sequence the setup questions across separate turns (worktree name → wait → base branch → wait). Keep each turn a single plain-text question. Consider stating the one-at-a-time rule explicitly so future preflight runs don't re-bundle.
- **Status:** RECORDED, not yet actioned. Test is live; tester will switch back to `or-preflight-1` and resume. Fix deferred until after the run (or per user direction).

### F2 — Phase agent (brainstormer) relays its user-question through the manager instead of asking in its own pane
- **Phase:** 1 (Brainstorm) — `or-brainstormer-1`.
- **Observation:** On its very first brainstorming question (Q1: target platform), `or-brainstormer-1` **SendMessaged the manager** with *"Please relay this question to the user,"* rather than emitting the question as plain text **in its own pane**. The brainstormer correctly asked one question at a time — but via the **wrong channel**. This is the **same defect class** already found and fixed for preflight (the relay anti-pattern).
- **Why it matters:** Breaks the load-bearing topology. The manager is supposed to be **silent** during Phase 1; phase-agent↔user dialogue is an **idle** event for the manager (no relay). Relaying every brainstorming question through the manager burns the one non-refreshable context the whole skill exists to preserve, and makes the manager a relay bottleneck for the entire dialogue.
- **Source (suspected):** The `claude-toolkit:or-brainstormer` agent body. The preflight relay-fix (2026-06-03, commit `10ea91a`) was applied to `preflight-brief.md` + `SKILL.md` Phase 0 + `manager-playbook.md` Initial Setup — but the **phase-agent bodies** (`or-brainstormer`, likely `or-plan-writer` and `or-finisher` too) may never have received the equivalent *"ask in your own pane, never relay"* guarantee.
- **Manager handling:** Did **NOT** relay (per design). → **Tester chose FIX-FORWARD (2026-06-03):** manager sent `or-brainstormer-1` a one-line channel-correction nudge (ask in own pane, never relay; SendMessage manager only for protocol tokens) and the run continues. Root-cause patch to the agent body remains **PENDING** (logged here for a later fix pass).
- **Candidate fix:** Add the same explicit *"you have your own pane; ask the user directly in plain text in your own turn; NEVER SendMessage the manager your user-facing questions or ask it to relay"* guarantee to the `or-brainstormer` agent — and audit `or-plan-writer` + `or-finisher` for the same gap. Generalizes the preflight fix to every user-facing teammate.
- **Tester directive (verbatim):** *"The brainstormer agent must talk to the user directly."* — this is the required behavior; the manager must not be a relay for phase-agent dialogue.
- **Status:** RECORDED. **Likely systemic** across all user-facing phase agents — highest-value finding so far.

Update the playbook idle taxonomy row, the "Plan→implementation go-ahead" subsection, and the communication-style sanctioned-surfacings list. Guard: this is correct **only** once F5 guarantees PLAN_COMPLETE always carries user approval.

### F7 — Supervisor doesn't use the canonical SPAWN handshake; tries to make the manager a heavyweight proxy (inject prompt + relay reports) — **SEVERE**
- **Phase:** 3 (Implementation) — `or-supervisor-1`, first worker dispatch (Task 0).
- **Observation:** Instead of the canonical terse handshake (`SPAWN / NAME / ROLE / MODEL` → manager spawns the typed `claude-toolkit:or-implementer` with `implementer-spawn-context.md` → replies `Spawned: <name>` → **supervisor briefs the worker directly** → **worker reports STATUS directly to the supervisor**), the supervisor:
  1. Sent a **prose** SPAWN request, not the `SPAWN / NAME / ROLE / MODEL` block.
  2. Requested subagent_type **`general-purpose`** (Red-Flag: worker type must be `claude-toolkit:or-<role>`), with a non-explicit model ("cheap/fast", not the required explicit `MODEL`).
  3. Provided the full task prompt **inline for the manager to inject**, rather than sending it to the worker directly after spawn.
  4. Explicitly asked the manager to **"relay the subagent's report back to me verbatim"** — stating its belief that, as "sole Agent-tool holder," the manager must proxy all worker I/O.
- **Root misconception:** The supervisor believes it cannot talk to workers directly. But workers are spawned as **background teammates** (`Agent` with `team_name` + `name`), and teammates can DM each other — so the supervisor must brief workers and receive their STATUS reports **directly**, with the manager only spawning / shutting-down. (`spawn-protocol.md`: supervisor SendMessages the worker the brief same-turn after `Spawned:`; playbook "Proactive Status Reporting": workers SendMessage the supervisor their STATUS.)
- **Why it matters (SEVERE):** If the manager relays every worker report, the manager's non-refreshable context burns down across all 15 tasks — **precisely the failure mode this whole skill exists to prevent** (Conservation Rules #5, #10; Red Flags). Highest-severity finding so far for the manager-context invariant.
- **Source:** `claude-toolkit:or-supervisor` agent body — it isn't loading/following `spawn-protocol.md`'s handshake, and misunderstands that workers are direct-DM-able teammates. (Possible the SDD wrapper inside `or-supervisor` assumes a single-context model where the supervisor itself owns the Agent tool.)
- **Manager handling (fix-forward):** Did **NOT** comply with the proxy/relay request. Corrected the supervisor: use the canonical `SPAWN / NAME / ROLE / MODEL`; I spawn the typed `or-implementer`; you brief the worker directly and it reports to you directly; reports never transit me. Preserved its (good) Task-0 brief — told it to send that to the worker directly.
- **Candidate fix:** Strengthen the `or-supervisor` agent body to (a) emit the canonical terse SPAWN block, (b) brief workers directly post-`Spawned:`, (c) expect worker STATUS reports directly (not via the manager). Reinforce in `supervisor-spawn-context.md` too. Audit the SDD wrapper's assumptions about who holds the Agent tool.
- **Status:** RECORDED — fix-forward (correcting the supervisor; awaiting a proper canonical SPAWN).

### F8 — Supervisor skips SDD's two-stage review between tasks (implementer-only dispatch)
- **Phase:** 3 (Implementation) — `or-supervisor-1`, Tasks 0–2.
- **Observation:** Every SPAWN the supervisor has sent is `ROLE: implementer`. It has **never** requested a `spec-reviewer` or `code-quality-reviewer`. Per-task flow has been implementer → worker reports DONE → SHUTDOWN + next implementer, with **no review stage and no fix loop**. For Task 1 the supervisor self-reported "sanity-check green" — a quick self-check, not the independent spec-compliance + code-quality review SDD prescribes.
- **Certainty:** The "not spawning reviewers" fact is **directly observable, not inferred** — reviewer subagents can only be created via the manager's SPAWN broker (the manager is the sole `Agent`-tool holder), and zero reviewer SPAWNs have arrived. Only the *cause* is inferred.
- **Expected (per SDD + this skill's topology):** Between each task, the supervisor spawns `or-spec-reviewer-task<N>` + `or-code-quality-reviewer-task<N>`, runs fix loops on findings, and runs `or-final-reviewer` at the end. The worker roster explicitly includes these reviewer identities.
- **Why it matters:** The two-stage review is the **core quality mechanism** of subagent-driven-development; skipping it means task output lands with only the implementer's own TDD as a gate — no independent spec/quality check. Defeats a primary value proposition of the orchestrator.
- **Source (suspected):** `claude-toolkit:or-supervisor` agent body — likely the same defect class as F7 (misunderstanding of the orchestration model); it may be running a degraded SDD that omits the reviewer SPAWNs, or conflating its own sanity-check with "review."
- **Manager handling:** Sent the supervisor a diagnostic query to confirm the cause; surfaced to the user (test director) with fix-forward vs pause-to-patch options.
- **Candidate fix:** Ensure `or-supervisor` drives SDD's full two-stage-review-between-tasks cycle (spec + code-quality reviewers per task, fix loops, final review). Likely couples with the F7 fix (correct the supervisor's model of the broker/teammate topology).
- **Diagnostic outcome (revealing):** The moment the manager sent the diagnostic query, the supervisor — *without explaining* — immediately sent a SPAWN for `or-spec-reviewer-task2`. This confirms the cause: the agent body **was not running the review cycle on its own**, but starts the moment it's nudged. Implication: **fix-forward is viable** — a one-time instruction makes the supervisor review.
- **Related protocol slip (sub-finding):** That reviewer SPAWN used `ROLE: reviewer` — **not a valid role token**. Valid reviewer roles are `spec-reviewer` and `code-quality-reviewer` (each maps to its own `claude-toolkit:or-*` subagent_type). The supervisor must send the precise token. (Candidate fix: same `or-supervisor` agent-body pass that addresses F7/F8 should pin the exact ROLE tokens.)
- **Self-correction nuance (refines the fix — KEY):** When challenged, the supervisor immediately and accurately self-diagnosed. It articulated SDD's review discipline *perfectly* ("the implementer's report is not to be trusted; 'mechanical' is not a license to skip review"), named its own rationalization ("the plan ships exact test+impl code, so it looked mechanical"), and proposed the exact correct flow (implementer → spec-reviewer → code-quality-reviewer → complete, with fix loops, citing the `b680d15→52da046` diff range and offering retro-review of Tasks 0–1). So the agent **knows** the rule and **self-corrects cleanly when nudged** — it just doesn't **initiate** the review loop autonomously. **Implication:** the F8 fix is narrow — make the per-task review loop **explicit / non-skippable** in the `or-supervisor` agent body (and kill the "mechanical ⇒ skip" rationalization in its prompt). The knowledge is already present; the *default behavior* is the only gap.
- **Status:** RECORDED → **RESOLVED-IN-RUN (resumed session).** `or-supervisor-2` (spawned with the F8 correction baked into its spawn-context) closed the Task 2 gate before starting any new task — spec-review PASS + code-quality "Ready to merge", tests independently re-run GREEN (3 pass / 0 fail), board #9 marked complete — then proceeded to Task 3 under the full per-task SDD cycle (implementer → spec-reviewer → code-quality-reviewer). **Fix-forward validated.** Root-cause patch to the `or-supervisor` agent body (make the per-task review loop non-skippable; kill the "mechanical ⇒ skip" rationalization) still PENDING for a later pass.

### F10 — Manager deferred the 200k handover to the user (offered a menu) instead of auto-executing it
- **Phase:** 3 → handover (manager-level; this session's behavior).
- **Observation:** On crossing 200k, the manager presented the user a **3-option menu** (wrap / cross-session handover / fix-forward) and waited for a choice, rather than **executing the handover automatically** and informing the user.

It is an **automatic, mandatory** process with the user merely **informed** at the end — NOT a menu to pick from. Conflating them into a menu was an unnecessary deferral that itself burned more manager context past 200k — defeating the safeguard, and risking the user picking "continue," which the threshold exists to prevent.
- **Candidate fix:** Reinforce in `manager-playbook.md` (Handover Ladder + Required Communication Style) that the 200k cross-session handover is **mandatory and auto-executed** — the manager does NOT offer wrap/continue alternatives; it executes, then emits the single sanctioned "recommend fresh session" surfacing. ### F11 — No first-class user trigger to resume after a cross-session manager handover
- **Phase:** handover / resume (skill UX).
- **Observation:** After the manager hands over at 200k and the user `/clear`s, there is **no documented first-class way for the user to trigger the continuation**. The skill is invocable as `/claude-toolkit:or-superpowers-at-scale [<idea>|<spec-path>|<plan-path>]` — none of those argument modes is "resume from a `manager-handover-N.md`." The user must **hand-craft a resume prompt** telling the fresh Claude to load the skill, read the handover doc, and follow the Fresh-Manager-Resume protocol. The handover doc + playbook describe what the fresh manager *does*, but not how the user *triggers* it.

AND put the exact copy-pasteable resume invocation in the `manager-handover-N.md` header so the user just pastes it.
- **Status:** RECORDED (surfaced by the tester's question "how does the user trigger a continuation?").

### F12 — No first-class supervisor→user channel for a non-blocking decision question (tier improvises a free-form "please relay")
- **Phase:** 3 (Implementation) — `or-supervisor-2`, Task 2 gate setup (resumed session).
- **Observation:** `or-supervisor-2` needed a **non-blocking user decision** — whether to retro-spec-review Task 1 (`constants.js`), the open question carried in from `iteration-1.md` §4c. The skill's topology defines a structured supervisor→user channel **only for PAUSE** (`PHASE_PAUSE`, with `action:` / `impact:` fields, intended for genuinely destructive / visible-to-others actions). There is **no first-class token for a non-blocking decision question**. The supervisor therefore improvised a free-form `"QUESTION FOR THE USER … please relay the user's call"` SendMessage to the manager; the manager surfaced it to the user and relayed the answer ("no retro-review") back. It worked, but via an undefined channel.
- **Why it matters:** A manager↔user relay of a phase-tier question is exactly the off-protocol improvisation the rest of the skill works to eliminate (cf. F2's relay anti-pattern). Without a defined token, behavior is inconsistent: a tier might block when it shouldn't, guess instead of asking, or mis-shape the question into a `PHASE_PAUSE` (whose `action:`/`impact:` fields don't fit a pure question). A decision-question and a destructive-action PAUSE are different semantics and deserve distinct, documented handling. The need is real and recurring — the handover/corrections explicitly pre-authorized "settle with the user," so tiers *will* hit this.
- **Source (suspected):** Protocol-surface gap — `manager-playbook.md` ("Phase Transitions & Idle Taxonomy" / PAUSE relay), `spawn-protocol.md`, and the `or-supervisor` / phase-agent bodies define only `PHASE_PAUSE` for depth-1→user communication. No `PHASE_QUESTION` (or equivalent) exists.
- **Candidate fix:** Add a first-class **non-blocking decision-question token** to the depth-1→manager protocol — e.g. `PHASE_QUESTION` with `question:` / `blocking: yes|no` / optional `options:` fields — plus a manager relay rule paralleling the PAUSE relay (surface one short paragraph to the user, return the answer; for `blocking: no` the tier keeps working meanwhile). Document it in the playbook idle taxonomy, the communication-style sanctioned-surfacings list, and `spawn-protocol.md`. Alternative: broaden the PAUSE relay with a `kind: question|action` discriminator. Either way, make the channel explicit so tiers stop improvising "please relay."
- **Status:** RECORDED — fix-forward (manager relayed the question + answer this run; no first-class channel exists yet). Tester directed recording with a correction note.

### F13 — Reviewer routes its completed report to the manager instead of its supervisor (worker-side mirror of F7)

### F25 — Test-director ruling: the manager is a PURE broker that NEVER originates teardown — so Conservation Rule #8 (manager culls strays) is a defect; the SUPERVISOR must reap the implementer on gate-close (it reaps reviewers but not the implementer)
- **Phase:** 3 — Task 13 → Task 14 transition.

The earlier "manager culls / treat idle as a cull-signal" idea is rejected outright.
- **Severity:** low–moderate operationally (no correctness impact) — but the Rule-8 contradiction is a clear design defect in the manager playbook.

### F28 — Manager-handover should capture the roster so the resuming manager does a CHEAP delta-check, not a full config.json read (context economy — sharpens F21)
- **Phase:** handover / resume (manager context economy).
- **Observation:** On a fresh-manager resume, the playbook's "reap orphans first" step and manager-handover-N's roster-reconciliation section both direct the successor manager to **enumerate `~/.claude/teams/<team>/config.json` in full**. That file is verbose — every member carries its full spawn `prompt`, timestamps, `subscriptions`, color, `backendType` — so a full read dumps a lot of low-value bytes into the one tier whose context is **non-refreshable**. manager-handover-3 already captures a curated roster (members + a disposition each: keep / reap / zombie / live-worker), yet still tells the manager to read live config anyway → the verbose read is **not actually saved**. Demonstrated live this session: the scribe `cat`'d the whole config to learn there are 4 members, pulling each member's full prompt into context when only the **name set** was needed.
- **Why it matters:** The resume roster check is **mandatory** (F21 — enumeration is the only thing that catches orphans the handover didn't expect; F23 — zombies; F25 — the resume reap of a dead session's orphans is the *one* sanctioned manager-originated teardown). But "mandatory" has been conflated with "full verbose read." The cost lands on the scarcest resource (manager non-refreshable context) at the worst moment (resume, while the manager is rebuilding state) — directly compounding F9/F18/F20 (manager context pressure). Cheaper-but-equally-safe is strictly better.
- **Tension to respect (why NOT just trust the handover roster):** F21/F23 proved config **lags reality** — handover roster assertions go stale (manager-handover-3 flags its *own* captured roster as maybe-stale: *"said this was reaped, but it's STILL listed"*). So the handover capture cannot **replace** the live check; it can only make it **cheap**.
- **Source:** Protocol-surface gap — `manager-playbook.md` ("Fresh manager resume" / "reap orphans first") and `assets/manager-handover-template.md` direct a full live enumeration and don't define a cheap delta-check; the template's roster capture (realized ad-hoc in manager-handover-3) isn't yet canonical.
- **Candidate fix (sharpens F21's "capture the roster" with a context-economy mechanism):**
  1. The manager-handover **template** captures the **enumerated live roster** at write time, one line of disposition per member (already partly in v3 — make it canonical + required, not ad-hoc).
  2. The fresh-manager resume protocol does **NOT** full-read config.json. It does a **names-only delta-check** — Grep the member `name`/`agentId` fields (a handful of lines) and diff against the handover's captured roster.
  3. Read **full member detail only for a delta** (a live member the handover didn't list, or a listed member now absent) — that delta is exactly the orphan/zombie to investigate and (per F25) reap.
  Net: common case = cheap Grep + the curated handover roster; the expensive read happens **only when reality has diverged**. Update `manager-playbook.md` + `manager-handover-template.md` to encode this.
- **Status:** RECORDED — surfaced by the test director; sharpens **F21** (capture the roster) with a context-economy mechanism (cheap delta-check). Couples F21 (staleness-safety), F23 (zombies), F25 (the resume reap is the one manager-originated teardown), F9/F18/F20 (manager context pressure). Reversible — flag if you'd prefer it reframed/removed.
